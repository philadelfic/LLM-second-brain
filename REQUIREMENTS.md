# Требования — LLM Second Brain

- Версия: 0.6 (согласовано, база для Фазы 1)
- Дата: 2026-08-29
- Журнал: 0.1 → 0.2 — имена методов `memory_*`; добавлены `memory_list` и
  `memory_get`; суммаризация заметок (отдельная LLM, своё подключение Ollama);
  `updated_at` во всех выдачах; update_note — перезапись целиком; дедуп-отказ.
  0.2 → 0.3 — режим «Б»: суммаризация фоновая (не блокирует save/update),
  reasoning суммаризатора не ограничивается; env `SUMMARY_THINK`,
  `SUMMARY_NUM_PREDICT`, `SUMMARY_TIMEOUT_SEC`.
  0.3 → 0.4 — soft delete (`deleted_at` + trash, undo оператором); пагинация
  `memory_list` (`offset`/`total`); backup (снапшоты БД); исправлено
  противоречие FR-4/FR-5 с режимом «Б».
  0.4 → 0.5 — фокус «легче моделям»: FTS5 `trigram` (русские словоформы);
  `snippet` + `summary_status` в выдачах; дедуп-фоллбек по FTS при отказе
  векторизации.
  0.5 → 0.6 — batch `memory_get` (список `ids`, чтение нескольких заметок
  за один вызов).

---

## 1. Обзор

LLM Second Brain — self-hosted сервис, представляющий LLM долговременную
память в виде общего банка заметок через протокол MCP (Model Context
Protocol). Основной харнес — Open WebUI (нативная поддержка MCP,
Streamable HTTP). Обслуживаются два внешних вызова LLM-инфраструктуры:
векторизация (Ollama, embedding-модель) и суммаризация (Ollama,
генеративная модель).

Сервис — «банк памяти»: он не задаёт вопросов, не гоняет RAG по внешним
документам и не строит интерфейсов для людей. Он только предоставляет
моделям 6 инструментов над общим банком заметок.

## 2. Цели и метрики успеха

**Цель 1 — распределённые знания с быстрым доступом.**
Знания живут в отдельном хранилище, а не вкомпилированы в системный промпт.
Любая модель в харнесе получает доступ к общему пулу по стоимости одного
tool-вызова (миллисекунды поиска + один запрос на кодирование запроса).

- Метрика: end-to-end время ответа `memory_search` ≤ 300 мс на 10 000 заметок
  (без учёта кодирования запроса в Ollama).
- Метрика: заметка, записанная в одной сессии, находится поиском в любой
  последующей.

**Цель 2 — снижение расхода токенов на стартовые запросы.**
Знания не вшиваются в каждый чат: фиксированный overhead остаётся маленьким,
содержание подтягивается адресно, а выдача — компактная (краткие содержания,
не целые заметки).

- Метрика: суммарный overhead на спецификацию инструментов + серверные
  инструкции ≤ ~1300 токенов.
- Метрика: выдачи `memory_search` состоят из кратких `summary` (~50–70
  токенов) + `snippet` (~30–40 токенов) на заметку, `memory_list` — только
  `summary`; полный текст модель тянет адресно через `memory_get`.

## 3. Не-цели (вне скоупа v1)

- Пользовательский интерфейс (веб-морда, админка) — не делается.
- Персонализация: per-user / per-model неймспейсы — одна общая база.
- Шифрование содержимого на диске.
- Загрузка внешних файлов/документов — только заметки от моделей.
- Function-фильтр Open WebUI для авто-инъекции на первом сообщении —
  опциональная Фаза 6, вне ядра.
- Публичный REST API как основной интерфейс — REST остаётся внутренней
  поверхностью (для оператора, диагностики и возможного Function-фильтра).

## 4. Актёры

| Актёр | Роль |
|---|---|
| LLM (любая модель в харнесе) | Потребитель и автор заметок через MCP-инструменты |
| Open WebUI (харнес) | MCP-клиент: подключает сервер, прокидывает инструменты моделям |
| Оператор (Олег) | Деплой, конфигурация, диагностика; доступ к файлу БД напрямую |
| Ollama-сервер векторизации (192.168.3.113) | `/api/embed`, `qwen3-embedding:8b` |
| Ollama-сервер суммаризации (192.168.3.112) | генеративная модель `ornith-1.5:35b` |

## 5. Функциональные требования

### 5.1 Инструменты MCP (полный набор — 6 штук)

Имена с префиксом `memory_*` — защита от коллизий имён с прочими
инструментами харнеса плюс семантический намёк модели на назначение.

#### FR-1 `memory_search`

- Вход: `query` (string, 1..`MAX_QUERY_CHARS`=512), `top_k` (int, 1..20,
  по умолчанию `DEFAULT_TOP_K`=5).
- Поведение: гибридный поиск — векторный (косинусная близость, sqlite-vec,
  **по полному тексту**) + полнотекстовый (FTS5/BM25), слияние через
  Reciprocal Rank Fusion.
- Выход: `{ results: [{ id, summary, snippet, summary_status, rrf_score,
  cosine, created_at, updated_at, author }], warning, hint }`
  - **Свободный текст заметки не возвращается** — только `summary` +
    `snippet` (первые `SNIPPET_CHARS` символов текста, чтобы модель оценила
    релевантность); полный текст по адресному запросу (`memory_get`).
  - `summary_status` (`ok` | `pending`) — модель видит, что `summary` может
    быть fallback-усечением, а не настоящей суммари.
  - Отсечение мусора: кандидатам с векторным hit — `cosine ≥
    SCORE_THRESHOLD` (дефолт 0.35, подстроить испытаниями); кандидаты,
    найденные только полнотекстом, порогом не режутся.
- Деградация: если векторизация запроса не удалась — поиск только по FTS5,
  `warning` с объяснением.
- Пустой результат: `results: []` + `hint` с советом переформулировать
  запрос шире (модели читают подсказки — канал обучения).

#### FR-2 `memory_list`

- Вход: `limit` (int, 1..50, по умолчанию 20), `offset` (int, ≥0, по
  умолчанию 0).
- Поведение: обзор памяти — заметки, **сортировка по `updated_at` по
  убыванию** (свежесть важнее возраста), пагинация `LIMIT :limit OFFSET
  :offset`; модель может обойти весь банк.
- Выход: `{ items: [{ id, summary, summary_status, created_at, updated_at,
  author }], total }` — без полных текстов; `total` — число активных заметок.

#### FR-3 `memory_get`

- Вход: `ids` (list[int], 1..`MAX_GET_BATCH`=20) — чтение одной или
  нескольких заметок за один вызов; `id` (int) — алиас для одного id
  (оборачивается в список).
- Поведение: возврат заметок целиком; отсутствующие/удалённые id
  пропускаются (в выдаче только найденные).
- Выход: `{ notes: [{ id, text, summary, summary_status, author,
  created_at, updated_at }] }` — массив, даже для одного id.
- Пустой результат (ни один id не найден) → мягкий ответ «заметки не
  найдены, возможно удалены».

#### FR-4 `memory_save`

- Вход: `text` (string, 1..`MAX_NOTE_CHARS`=2000 символов).
- Поведение:
  1. Валидация длины.
  2. Синхронное кодирование текста (Ollama векторизации, обычно 20–150 мс).
  3. **Дедуп**: топ-1 по косинусной близости среди существующих. Если
     близость ≥ `DEDUP_SIMILARITY` (0.92) — запись **не создаётся**:
     `{ duplicated: true, id: <существующей>, text: <её текст>,
        hint: "почти идентичная заметка уже есть; чтобы уточнить — вызови
        memory_update(…) (сначала memory_get, чтобы не потерять детали)" }`.
     Порог ловит почти дословные повторы; перефразы (обычно 0.80–0.85)
     сохраняются как новые заметки.
  4. Иначе: INSERT заметки (`summary=''`, `summary_status=pending`) +
     запись вектора → `{ id, stored: true, summary_pending: true }`.
  5. **Суммаризация** — фоновая (режим «Б», см. 5.5): не блокирует запись;
     воркер генерирует `summary`; до готовности в выдачах — fallback-усечение
     текста; при отказе суммаризатора — повтор по back-off.
- Отказ Ollama векторизации (шаг 2): заметка всё равно сохраняется
  (`vector_status=pending`); дедуп деградирует к FTS — точное/почти точное
  совпадение нормализованного текста ловит дословные дубли, перефразы
  пропускаются (warning в ответе); фоновый воркер до-векторизует.
- Требование к содержимому (в описании инструмента): заметка
  самодостаточна — подлежащее, детали, даты; без местоимений без антецедента.

#### FR-5 `memory_update`

- Вход: `id` (int), `text` (1..`MAX_NOTE_CHARS`).
- Поведение: **перезапись текста целиком** (сознательное решение — модель
  формулирует заметку заново, не приращивает хвосты; полноту деталей
  обеспечивается правилом «сначала memory_get»), обновление `updated_at`,
  синхронная ре-векторизация; суммаризация — фоновая (режим «Б», §5.5),
  не блокирует запись; при отказах — соответствующие `pending`-статусы
  и фоновые догенерации.
- Ошибка: неизвестный `id` → «заметка не найдена».

#### FR-6 `memory_delete`

- Вход: `id` (int).
- Поведение: **soft delete** — заметка помечается удалённой (`deleted_at`),
  исчезает из `memory_search`/`memory_list`/`memory_get`; строка, FTS-индекс
  и вектор физически сохраняются (trash).
- Undo: оператор снимает `deleted_at` напрямую в БД (у него есть доступ);
  инструмент `memory_restore` для моделей — в «развитие».
- Сознательное решение: модели могут удалять; страховка от массового
  удаления — soft delete + trash (физической потери нет).

### 5.2 Метаданные заметки

- `author` — имя модели-автора, если харнес передаёт метаданные вызова;
  иначе `unknown` (`AUTHOR_DEFAULT`).
- `created_at`, `updated_at` — UTC ISO-8601; **`updated_at` присутствует во
  всех выдачах** (search/list/get) и обновляется при каждом изменении.
- `deleted_at` — UTC ISO-8601 или NULL; NULL = заметка активна. Ставится
  при `memory_delete` (soft delete); удалённые заметки исключаются из всех
  выдач.

### 5.3 Векторизация

- Кодирование через Ollama `POST /api/embed` на `OLLAMA_BASE_URL`, модель
  `EMBEDDING_MODEL` (`qwen3-embedding:8b`), размерность `EMBEDDING_DIM` (4096).
- Вектора строятся **от полного текста** заметки (не от summary) — поиск
  остаётся точным; суммаризация на качество retrieval не влияет.
- Неудачная векторизация не ломает пользовательские операции: заметка
  сохраняется, до-векторизация фоновым воркером с экспоненциальным back-off
  (старт `PENDING_RETRY_SEC`=30, ×2, max 15 мин).

### 5.4 Поиск: требования к качеству

- Гибрид обязателен: чисто векторный поиск пропускает точные токены
  (идентификаторы, названия сервисов, даты), чисто полнотекстовый не ловит
  перефразы.
- FTS5 на токенизаторе `trigram` (подстроки ≥3 символов): ловит русские
  словоформы/склонения и точные токены без внешнего стеммера; требует
  SQLite ≥ 3.34.
- Единый `top_k` управляет финальным размером выдачи (кандидатов — по 50 из
  каждого источника).

### 5.5 Суммаризация

- **Назначение:** выдача в `memory_search`/`memory_list` краткого содержания
  вместо полного текста — экономия токенов в каждом ответе.
- **Генерация:** отдельная LLM — сервер `SUMMARY_OLLAMA_BASE_URL`
  (192.168.3.112), модель `SUMMARY_MODEL` (`ornith-1.5:35b`; семейство
  Qwen3.5-MoE, 35.5B, Q4_K_M, ~22.6 ГБ, контекст 262k), лимит
  `MAX_SUMMARY_CHARS`=200, одно предложение, на языке заметки, с сохранением
  имён/чисел/дат, без вступлений.
- **Thinking не ограничивается (режим «Б», решение 2026-08-29):** модель
  может рассуждать сколько нужно — рассуждения приходят в отдельное поле
  `thinking` и в БД не попадают, сохраняется только `message.content`.
  В Ollama нет отдельного лимита на `content` (бюджет `num_predict` общий
  на thinking+content), поэтому: бюджет задаётся щедрым
  (`SUMMARY_NUM_PREDICT`=1500), контроль времени — клиентский таймаут
  `SUMMARY_TIMEOUT_SEC`=60 с; при `SUMMARY_THINK=false` в вызов явно
  добавляется `"think": false`. Страховка: пустой `content` → трактовка
  как отказ → fallback + `summary_status=pending`.
- **Момент генерации: фоново, не блокирует запись.** `memory_save` и
  `memory_update` возвращаются сразу (в ответе — `summary_pending: true`);
  в БД пишется `summary=''` с `summary_status=pending`; до готовности в
  выдачах search/list/get используется штатный fallback «первые
  MAX_SUMMARY_CHARS символов текста». Фоновый воркер генерирует суммари;
  при отказе — повтор по back-off.
- **Хранение:** отдельное поле `summary` в таблице заметок; не векторизуется
  и не индексируется FTS.

## 6. Нефункциональные требования

### NFR-1 Развёртывание

- Один контейнер Docker (compose), `restart: unless-stopped`, non-root.
- Постоянные данные — volume на `/data` (файл `notes.db`).
- Порт `PORT` (8080) — для MCP (`/mcp`), REST и `/health`.

### NFR-2 Аутентификация

- Статический Bearer-токен (`MCP_AUTH_TOKEN`) на все MCP- и REST-ручки,
  кроме `/health`. Пустой токен при старте — фатальная ошибка конфигурации.

### NFR-3 Надёжность

- Полная персистентность при перезапусках.
- Отказ любого из двух внешних LLM-серверов не ломает CRUD:
  векторизация → `vector_status=pending` (поиск деградирует к FTS),
  суммаризация → fallback-усечение + `summary_status=pending`.
- Оба внешних сервера могут быть недоступны на старте — сервис поднимается.
- Резервное копирование: периодический снапшот БД (SQLite `backup` API,
  онлайн, без остановки) в `BACKUP_DIR`, ротация по `BACKUP_KEEP`.

### NFR-4 Наблюдаемость

- Логи stdout (JSON, `LOG_LEVEL`): вызовы инструментов с латентностью и
  числом результатов; тексты запросов — первые 80 символов, содержимое
  заметок в логи не пишется.
- `/health` (без токена): `{ status, embedding_ok, summarizer_ok,
  notes_count, pending_vector, pending_summary }` — и для docker healthcheck,
  и оператору.

### NFR-5 Производительность

- `memory_search` p95 ≤ 300 мс на 10 000 заметок (без учёта кодирования
  запроса).
- `memory_get`/`memory_list` p95 ≤ 50 мс.
- `memory_save`/`memory_update` p95 ≤ 1.5 с (embedding ~0.1–0.2 с + дедуп;
  суммаризация в синхронном пути отсутствует — режим «Б»). Замер
  2026-08-29: тёплый вызов суммаризатора 3–8 с с рассуждением — удалён
  из критического пути записи; холодный старт после простоя (~22.6 ГБ)
  сглаживается `keep_alive≈15m`.
- Объёмы: до ~50 000 заметок без смены архитектуры (16 КБ/вектор 4096
  float32; brute-force скан sqlite-vec на этих объёмах приёмлем).

### NFR-6 Ограничения

- `MAX_QUERY_CHARS`=512, `MAX_NOTE_CHARS`=2000, `MAX_SUMMARY_CHARS`=200,
  `SNIPPET_CHARS`=120, `MAX_GET_BATCH`=20, `top_k` ≤ 20, `limit` ≤ 50.
  Значения env-переопределяемы.

## 7. Совместимость

- MCP: спецификация 2025-06-18, транспорт **Streamable HTTP only**,
  аутентификация `Authorization: Bearer`.
- Open WebUI (последние версии): подключение как внешний MCP в админке,
  инструменты доступны всем моделям; одна общая база.
- Прочие MCP-совместимые клиенты — без изменений.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OLLAMA_BASE_URL` | **обязательна** | Ollama векторизации, напр. `http://192.168.3.113:11434` |
| `EMBEDDING_MODEL` | `qwen3-embedding:8b` | embedding-модель |
| `EMBEDDING_DIM` | `4096` | размерность (фиксируется при создании ДБ) |
| `SUMMARY_OLLAMA_BASE_URL` | **обязательна** | Ollama суммаризации, напр. `http://192.168.3.112:11434` |
| `SUMMARY_MODEL` | **обязательна** | генеративная модель суммаризации, `ornith-1.5:35b` |
| `MAX_SUMMARY_CHARS` | `200` | лимит краткого содержания |
| `SNIPPET_CHARS` | `120` | длина фрагмента текста в выдаче `memory_search` |
| `MAX_GET_BATCH` | `20` | максимум id в одном `memory_get` |
| `SUMMARY_THINK` | `true` | разрешить рассуждения суммаризатора (при `false` в вызов идёт `"think": false`) |
| `SUMMARY_NUM_PREDICT` | `1500` | бюджет генерации суммаризатора (общий на thinking+content) |
| `SUMMARY_TIMEOUT_SEC` | `60` | клиентский таймаут вызова суммаризатора |
| `PORT` | `8080` | порт HTTP-сервера |
| `MCP_PATH` | `/mcp` | путь MCP-сервера (Streamable HTTP) |
| `MCP_AUTH_TOKEN` | **обязательна** | Bearer-токен без умолчания |
| `DB_PATH` | `/data/notes.db` | путь к SQLite |
| `DEFAULT_TOP_K` | `5` | top_k по умолчанию в `memory_search` |
| `DEFAULT_LIST_LIMIT` | `20` | limit по умолчанию в `memory_list` |
| `SCORE_THRESHOLD` | `0.35` | порог косинусной близости для отсечения |
| `DEDUP_SIMILARITY` | `0.92` | порог «почти дубликата» в `memory_save` |
| `RRF_K` | `60` | константа слияния RRF |
| `MAX_NOTE_CHARS` | `2000` | лимит длины заметки |
| `MAX_QUERY_CHARS` | `512` | лимит поискового запроса |
| `PENDING_RETRY_SEC` | `30` | стартовый интервал до-векторизации/досуммаризации |
| `LOG_LEVEL` | `INFO` | уровень логов |
| `AUTHOR_DEFAULT` | `unknown` | author, если харнес не передал метаданные |
| `BACKUP_DIR` | `/data/backups` | каталог снапшотов БД |
| `BACKUP_INTERVAL_SEC` | `86400` | интервал снапшотов (сутки) |
| `BACKUP_KEEP` | `7` | число хранимых копий (ротация) |

**Важно:** смена `EMBEDDING_DIM` после создания БД требует переиндексации
(размерность фиксируется в DDL vec0-таблицы). При несовпадении старта —
понятная ошибка; переиндексация — скрипт `scripts/reindex.py` (Фаза 3).

## 9. Ограничения и риски

| Риск | Митигация в v1 |
|---|---|
| Одна общая база → шум из соседних доменов | качество гибридного поиска + порог отсечения; неймспейсы — развитие |
| Модели пишут мусор и дубли | `MAX_NOTE_CHARS`, дедуп-отказ с возвратом существующего id, ручки update/delete, подсказки-обучения в ответах |
| Человек не видит данные через UI | принято намеренно; оператору — файл БД напрямую |
| Отказ Ollama векторизации | запись не теряется (`vector_status=pending`), поиск деградирует к FTS, `/health` сигнализирует |
| Отказ суммаризатора (35B, ~22.6 ГБ, холодный старт после простоя) | запись не блокируется (режим «Б»); в выдаче fallback-усечение + `summary_status=pending`; повтор по back-off; `keep_alive≈15m` против выгрузки |
| Отставание LLM-суммари у свежих заметок (секунды–минуты) | штатно для режима «Б»: сначала усечение текста; качество поиска не страдает (вектор по полному тексту) |
| Модель не догадывается искать | описания инструментов + `hint`/`warning` + MCP-инструкции; далее Function (Фаза 6) / системный промпт харнеса |
| Смена embedding-модели/размерности | невалидный векторный индекс — отказ старта + скрипт переиндексации |
| Смена `SUMMARY_MODEL` | безопасна: пересуммаризация по желанию, обычное поле данных |
| Потеря данных (один файл БД) | периодические снапшоты (SQLite backup API) + ротация |

## 10. Roadmap

Ритм: один шаг → тесты → отчёт → «дальше».

1. **Фаза 1 — каркас.** Репо, Dockerfile, compose, env-парсер, FastAPI +
   FastMCP (`/mcp`), `/health`, Bearer-миддлварь. Проверка: контейнер
   собирается, MCP handshake работает, поле `instructions` доносится
   (практический эксперимент), токен фильтрует.
2. **Фаза 2 — хранилище.** Схема SQLite (notes + FTS5-триггеры, поля
   `summary`, `vector_status`, `summary_status`), CRUD всех 6 методов
   (без внешних вызовов: summary — фоллбек-усечение), тесты.
3. **Фаза 3 — векторизация и поиск.** Клиент Ollama (`/api/embed`),
   sqlite-vec, гибридный RRF-поиск, дедуп в `memory_save`, фоновая
   до-векторизация, скрипт переиндексации. Тесты: unit с детерминированным
   мок-эмбеддером + интеграционные на живой Ollama (маркер, скип при
   недоступности).
4. **Фаза 4 — суммаризация (фоновая, режим «Б»).** Клиент ко второй Ollama
   (192.168.3.112, `ornith-1.5:35b`; thinking не ограничиваем, таймаут 60 с),
   очередь `pending_summary` как штатный путь, fallback-усечение в выдаче
   до готовности. Замеры: латентность фоновой генерации, влияние reasoning
   на качество summary на реальных заметках, актуальность догенерации.
5. **Фаза 5 — hardening и деплой.** Лимиты, логирование, backup (снапшоты
   БД), README с подключением Open WebUI, сборка образа, подъём на целевом
   сервере.
6. **Фаза 6 (опционально) — Function-фильтр Open WebUI** для авто-подмешивания
   топ-K суммари к первому сообщению чата.
