## BUG-001 — Многословные запросы `memory_search` теряют релевантные заметки

- **Статус:** открыт
- **Дата:** 2026-08-30
- **Серьёзность:** высокая — бьёт по цели FR-1 «заметка, записанная в одной сессии, находится поиском в любой другой» (REQUIREMENTS.md, §FR-1 / метрики качества §5.4)
- **Окружение:** рабочий инстанс (appsrv); на момент воспроизведения в БД 6 заметок, из них #24–#26 записаны за ~5 минут до теста (суммари уже построены фоновым воркером)

### Воспроизведение (top_k=5)

| Запрос | Выдача | Ожидание |
|---|---|---|
| `СУБО` | #25, #22, #24, #23 | ✅ ок |
| `chat_id` | #26, #22, #23 | ✅ ок |
| `профиль Олега СУБО 2020 команда` | `[]` + hint «ничего не найдено» | #24, #25 |
| `openwebui chat_id` | #22, #23 (нерелевантные) | #26 |
| `chat_id openwebui docker sqlite` | #22, #23 | #26 |

Однословные запросы работают стабильно; многословные — либо пусто, либо нерелевантные соседи вместо очевидного попадания.

### Диагноз (по коду `app/services/search.py`)

1. **FTS-ветка: `_match_expression` склеивает слова ≥3 символов через `AND`.**
   Один токен, которого нет в тексте заметки как подстроки, обнуляет FTS-кандидатуру этой заметки целиком.
   Примеры: «openwebui» — в текстах только «Open WebUI» / «open-webui», токен-подстрока не встречается → FTS молчит для #26 при любом запросе с этим словом; «профиль» / «Олега» / «команда» не являются подстроками в #24/#25 («Олег», «команды») → FTS пуст для запроса про профиль.
   При этом docstring FTS-ветки декларирует «порогу не подлежит» — фактически AND превращает ветку в all-or-nothing на уровне заметки.
2. **Векторная ветка: порог отсечения до слияния + окно `vector_status=pending` у свежих заметок.**
   Только что сохранённая заметка (воркер ещё не построил вектора) невидима векторной ветке — ни чанк-векторов, ни полного вектора. Если одновременно FTS-ветка убита AND-ом (п.1), заметка полностью выпадает из выдачи. Наблюдение: для запроса «openwebui chat_id» векторная ветка выдала нерелевантные #22/#23, а релевантный #26 не попал — либо порог SCORE_THRESHOLD, либо лаг векторизации, либо ранжирование эмбеддинга.
3. **Hint вводит в заблуждение:** «ищется по подстрокам от 3 символов» верно только для однословных запросов. При AND-семантике многословный запрос требует, чтобы ВСЕ слова были подстроками.

### Гипотезы исправления (обсудить, не решение)

- **FTS:** OR вместо AND с BM25-ранжированием (RRF-слияние и так отсечёт шум); либо AND только по 2–3 самым discriminative-токенам; либо нормализация токенов при построении выражения (lowercase, склейка/разбивка дефисов и пробелов: «open-webui» → «open» + «webui»).
- **Свежие заметки:** синхронная векторизация полного текста на `save` (одна заметка — дёшево), чанки оставить фоновому воркеру. Закрывает окно полной невидимости.
- **Hint:** уточнить формулировку под фактическую семантику.

### Обход до фикса

Искать короткими запросами из 1–2 точных токенов, которые гарантированно есть в тексте заметки («СУБО», «chat_id»).
