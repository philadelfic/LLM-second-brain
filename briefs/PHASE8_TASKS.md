## Этап 1 — save мгновенный (embed + summarize уходят в фон параллельно)

Цель: `memory_save`/`memory_update` перестают ждать векторизацию. Текст
пишется сразу (`vector_status='pending'`), векторизация и суммаризация
догоняются фоновым воркером (очереди `pending_vector`/`pending_summary`
уже существуют — их не переписывать, только задействовать).

### Задача 1.1 — убрать синхронный embed из save/update

Файл: `app/services/notes.py`.

Что сделать:
1. В `save()`:
   - Убрать `vector = self._note_vector(text)` и ветку косинус-дедупа
     (`self._dedup.find_by_cosine(vector)`).
   - Оставить **дословный** дедуп по тексту `self._dedup.find_by_text(text)`
     (он мгновенный — SQL/FTS, не требует Ollama; перефразы он не ловит,
     это теперь зона фонового дедупа Этапа 2).
   - INSERT сразу с `vector_status="pending"` (не `"ok"`), чанки раскладывать
     чистым сплиттером (`_chunks_of`), но **без** вектора (`_store_chunks(..., None)`).
   - `_notify_summary_pending()` — оставить.
   - Ответ успеха: `{id, stored: True, summary_pending: True}` — **без**
     `warning` (векторизация теперь всегда фоновая, а не «отложена из-за отказа»).
2. В `update()`:
   - Убрать `vector = self._note_vector(text)` и `vectors.upsert(...)`.
   - UPDATE text сразу с `vector_status='pending'`, чанки пересоздаются
     без векторов (`_store_chunks(..., None)`).
   - Ответ не меняется: `{id, updated: True, summary_pending: True}`.
3. Удалить ставшие ненужными `_note_vector()` и константу
   `WARNING_VECTOR_PENDING` (если больше нигде не используется).
4. Обновить docstring модуля и `save()`/`update()`: описать, что векторизация
   и дедуп по косинусу теперь фоновые.

Критерии приёмки:
- `save`/`update` не вызывают `embedding.embed()` синхронно (проверяется
  фейк-эмбеддером, который падает/считает вызовы).
- После `save` в БД `vector_status='pending'`, строка заметки есть, чанки
  есть, векторов нет.
- Дословный дубль по-прежнему отсекается синхронно (`duplicated: True`).
- Все существующие юнит-тесты зелёные (кроме тех, что явно проверяли
  синхронный embed — их обновить в Задаче 1.3).

## Этап 2 — фоновый дедуп (вариант B: косинус-кандидаты → сведение)

Цель: после того как воркер довекторизовал заметку, найти косинус-кандидатов
и свести дубли. Судья (LLM) — на Этапе 3; на Этапе 2 сведение работает по
косинусу (порог), без LLM.

### Задача 2.1 — косинус-кандидаты после векторизации

Файлы: `app/services/worker.py`, `app/services/dedup.py`, `app/config.py`.

Что сделать:
1. В `DeduplicationService` добавить метод поиска **топ-N** кандидатов по
   косинусу (сейчас `find_by_cosine` возвращает топ-1 с порогом
   `DEDUP_SIMILARITY=0.92`). Нужен метод `find_candidates(vector, top_n)`,
   возвращающий список `(note_id, cosine)` с порогом-кандидатом ниже
   (перефразы ~0.80–0.85).
2. Новые env (в `config.py` + `docker-compose.yml`):
   - `DEDUP_CANDIDATE_TOP_N` (int, default 3) — сколько кандидатов брать;
   - `DEDUP_CANDIDATE_SIMILARITY` (float, default 0.80) — нижний порог
     косинуса для кандидата (валидация 0..1).
3. В воркере: после довекторизации заметки (в `process_pending`, где
   `vector_status` становится `'ok'`) — для каждой свеже-векторизованной
   заметки найти кандидатов и, если есть, пометить/запустить сведение
   (Задача 2.2). Продумать, как не зациклить и не обрабатывать одну пару
   дважды (например, обрабатывать только «новую» заметку против «старых»).

Критерии приёмки:
- После довекторизации заметки-перефраза кандидаты находятся.
- Юнит-тесты на `find_candidates` (топ-N, порог) зелёные.

### Задача 2.2 — сведение дублей (объединение суммаризатором)

Файлы: `app/services/worker.py`, `app/services/summary.py`, `app/services/notes.py`.

Что сделать (вариант B из брифа):
1. Когда кандидат признан дублем (на Этапе 2 — по косинусу ≥ порога):
   - отправить **оба текста** в суммаризатор с новым промптом «объедини два
     текста в один, сохрани все факты/имена/числа/даты» (новый метод
     `SummaryService.merge(text_a, text_b)` или отдельный промпт);
   - **обновить более ранний** дубль (меньший `id`) через логику
     `NoteService.update` (ре-векторизация + ре-суммаризация стандартно);
   - **новую (позднюю) заметку** — soft delete (`deleted_at = now`).
2. Сведение должно быть идемпотентным и не ломать данные при отказе
   суммаризатора (NFR-3): при отказе объединения — оставить обе заметки,
   статус дедупа pending, повторить по back-off.

Критерии приёмки:
- Пара «перефраз» → ранняя заметка обновлена объединённым текстом, поздняя
  soft-deleted.
- Отказ суммаризатора не портит заметки (обе живы, повтор по back-off).
- Юнит-тесты на сведение (фейк-суммаризатор) зелёные.

## Этап 3 — LLM-судья `ornith-1.5:35b`

Цель: заменить/дополнить косинус-решение судьёй-LLM. Судья решает «дубль/не
дубль» по паре текстов; косинус остаётся предфильтром (топ-N кандидатов).

### Задача 3.1 — JudgeService + env

Файлы: `app/services/judge.py` (новый), `app/config.py`, `app/services/__init__.py`,
`app/main.py`, `docker-compose.yml`.

Что сделать:
1. Новый сервис `JudgeService` — клиент Ollama `POST /api/chat`, по образцу
   `SummaryService` (синхронный `httpx.Client`, `transport` для тестов,
   `last_attempt_ok` для `/health`).
   - Промпт: «Определи, являются ли два текста дублями (одна и та же мысль,
     пересказанная другими словами). Ответь строго: ДУБЛЬ или НЕ ДУБЛЬ».
   - Парсинг вердикта: `message.content` начинается с `**ДУБЛЬ**` /
     `**НЕ ДУБЛЬ**` (markdown-жирный) — стрипать `**`/искать подстроку
     «ДУБЛЬ»/«НЕ ДУБЛЬ»; `message.thinking` игнорировать.
   - `think: false` в запросе (судья не думает).
2. Новые env (обязательные — без умолчания, как `SUMMARY_*`):
   - `DEDUP_JUDGE_OLLAMA_BASE_URL` (str, обязательная) — `http://192.168.3.112:11434`;
   - `DEDUP_JUDGE_MODEL` (str, обязательная) — `ornith-1.5:35b`;
   - `DEDUP_JUDGE_THINK` (bool, default `false`);
   - `DEDUP_JUDGE_NUM_PREDICT` (int, default 256 — судье хватает на вердикт);
   - `DEDUP_JUDGE_TIMEOUT_SEC` (int, default 30).
   Валидация NFR-6: URL http(s), num_predict/timeout ≥ 1.
3. Подключить в `build_services`/`Services` и `main.py` (DI, как summary).

Критерии приёмки:
- Юнит-тесты `JudgeService` (MockTransport): корректный парсинг
  `**ДУБЛЬ**`/`**НЕ ДУБЛЬ**`, отказ при пустом content/не-200/не-JSON.
- `think:false` присутствует в теле запроса.

### Задача 3.2 — интеграция судьи в дедуп

Файлы: `app/services/worker.py`, `app/services/dedup.py`.

Что сделать:
- В фоновом дедупе (Этап 2) заменить косинус-решение на судью: для каждого
  косинус-кандидата (топ-N) спросить `JudgeService.judge(text_new, text_cand)`;
  если «ДУБЛЬ» → сведение (Задача 2.2).
- Косинус остаётся предфильтром (кандидаты), финальное решение — судья.

Критерии приёмки:
- Перефраз, который косинус не ловит на 0.92, судья признаёт дублем → сведение.
- Разные заметки судья признаёт «НЕ ДУБЛЬ» → не сводятся.
- Юнит-тесты с фейк-судьёй зелёные.
