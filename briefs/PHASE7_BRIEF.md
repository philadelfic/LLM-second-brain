# Фаза 7 — чанк-индексация длинных заметок

Ты реализуешь **Фазу 7** проекта **LLM Second Brain** — self-hosted MCP-сервера
долговременной памяти для LLM (харнес Open WebUI). Фазы 1–6 завершены, сервис
в боевой эксплуатации на appsrv (192.168.3.111:8080), живые заметки в БД.

## 1. Проблема

`MAX_NOTE_CHARS=20000` (решение Олега 2026-08-29), но векторов пока **один на
заметку** (полный текст) — на длинной заметке вектор «размазывает» семантику,
локальный поиск по факту внутри неё проседает. Решение: заметка хранится
и отдаётся **целиком** (не трогаем), а **вектора** строятся по чанкам.

## 3. Решённые механики, которые переиспользуем

- `meta`-таблица в БД (init_db, коммит b972386) — автореиндексация при смене
  EMBEDDING_MODEL/EMBEDDING_DIM. **Расширить**: чанковые параметры тоже в
  meta (chunk_size, chunk_overlap, chunk_min_target); смена → полная
  пере-чанковка + реиндексация всех заметок (включая trash), same механика.
- Пакетный воркер с back-off; таймауты; fakes/HashEmbedder в тестах.
- compose = единственное место конфигурации (без .env, литы-значения).

## 4. Параметры (все — в docker-compose.yml)

`TEXT_SPLITTER=tiktoken` (фикс. encoding cl100k_base, env не обязателен),
`CHUNK_SIZE=1024` (токенов), `CHUNK_OVERLAP=180` (токенов),
`CHUNK_MIN_TARGET=200` (токенов: хвостовой чанк меньше — слить с предыдущим),
`EMBEDDING_BATCH_SIZE=32` (чанков в одном embed-запросе),
`EMBEDDING_CONCURRENT_REQUESTS=3` (параллельных embed-запросов воркера).
Markdown Header Splitter — НЕ делаем (заметки моделей не markdown-документы,
зафиксировано как решение).

NFR-лимиты по умолчанию из §8: заметка 20 000 симв. ≈ 7 500 токенов ≈ ≤9
чанков — управляемо; типичная заметка ≤3 000 симв. = 1 чанк (схема
вырождается в текущую). tiktoken: добавить зависимость, пресобрать BPE-файл
в образ (`RUN python -c "import tiktoken; tiktoken.get_encoding('cl100k_base')"`)
иначе холодный контейнер без сети не стартуетsumm своим делом — проверь.

## 5. Схема (черновик)

```
notes_chunks (id INTEGER PK, note_id FK->notes, idx INT,
              text TEXT NOT NULL, tokens INT NOT NULL,
              UNIQUE(note_id, idx))
DELETE/cascade при update/delete заметки (физическая чистка чанков
deleted-заметки — при физическом удалении оператором, как сегодня).
notes_chunks_vec USING vec0(chunk_id INTEGER PK, embedding float[EMBEDDING_DIM]
              distance_metric=cosine)
meta: + chunk_size, chunk_overlap, chunk_min_target
notes_vec — остаётся (полный текст): дедуп + точный retrieval мелких заметок.
```

## 6. Логика

- **NoteService.save/update**: полный вектор заметки — как сейчас (sync,
  дедуп не меняется); чанки: split → если 1 чанк и текст ≤ CHUNK_SIZE —
  вектора чанка = полный вектор заметки (не кодировать дважды — reuse);
  иначе чанковую очередь → pending; при update — старые чанки удаляются,
  новые pending. DELETE (soft) — чанки остаются (trash), у физического
  удаления — чистить.
- **SearchService**: запрос → вектор → KNN по чанкам (топ-50) → агрегация
  до заметок: лучший чанк заметки задаёт cosine; для заметок без готовых
  чанков — fallback на вектор полного текста (notes_vec) как сейчас;
  FTS-плечо (BM25 по notes) — без изменений; RRF поверх агрегированных
  списков как раньше. **snippet — из лучшего чанка** (первые
  SNIPPET_CHARS символов чанка). Косинус отдачи — cosine лучшего чанка
  (сравним с порогом SCORE_THRESHOLD).
- **Воркер**: очередь pending-чанков; партии `EMBEDDING_BATCH_SIZE`,
  параллелизм `EMBEDDING_CONCURRENT_REQUESTS` (Semaphore + asyncio.gather);
  back-off не меняется; `embedding_ok` агрегируется как сейчас.
- **Автореиндексация**: смена любого чанк-параметра или модели/размерности →
  полная пере-чанковка + вектора чанков с нуля, события
  reindex_started/reindex_done; база → pending, воркер догоняет.

## 7. Ритм

Один шаг → тесты → отчёт → жди «дальше». Предлагаемое разбиение
(корректируй по ходу):

1. Зависимость tiktoken + пре-кэш в Dockerfile, `splitter.py` (токен-сплит
   с окном/overlap/минимальным хвостом), параметры в Settings + compose,
   unit-тесты сплиттера (рус/англ, границы, overlap-стыки, min target).
2. Storage: notes_chunks + notes_chunks_vec + meta-расширение + миграции.
   Юнит: создание/каскады/уникальность.
3. NoteService: save/update/delete — чанковка, reuse единичного чанка,
   физическая чистка. Юнит: 1-чанная заметка ≠ дубликат чанка-векторов.
4. SearchService: агрегация чанк-хитов, fallback на полный вектор,
   snippet из лучшего чанка. Юнит: ранк по лучшему чанку, фоллбек.
5. Воркер: обработка чанковой очереди, batch+concurrency, вычитывающая
   партия. Юнит: 3 одновременных, бахчи по 32 (фейк-счётчики).
6. Автореиндексация чанк-параметров: тесты смены CHUNK_SIZE → пере-чанковка.
7. compose/README/ARCHITECTURE-правки, интеграционные @live (реальная
   Ollama: релевантность на длинной 15kFixture-заметке, сравнение с Фазой 3).
8. Деплой на appsrv (compose up -d), смок: сохранить заметку 15k, проверить
   чанки в БД и поиск по школьному фрагменту из её середины.
