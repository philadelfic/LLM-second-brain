# Фаза 9: компактные контракты MCP-выдач (постановка)

Дата: 2026-08-30. Постановка утверждена Олегом (2026-08-30, чат llm-second-brain).
База: HEAD 11dc2e6 (Фаза 8 завершена, 473 passed / 11 deselected).

## 0. Смысл и границы

Адресат системы — модели-клиенты через MCP. Их рабочий цикл: искать → открыть
адресно → уточнить. Всё, что модель не использует для принятия решения, из
MCP-выдач уходит. REST — поверхность оператора/диагностики и стабилизации:
**не меняем вообще ничего** (контракты ответов REST сегодня зафиксированы
в rest.py и тестах — остаются как есть).

Из этого следует архитектурное решение: сервис-слой (app/services/*) сохраняет
текущие полные ответы без изменений; компактная выдача формируется в
MCP-транспорте (app/transport/mcp.py) как маппинг «полный контракт → компактный».
Это единственное место, где меняется формат ответа модели.

Запрет касания: app/transport/rest.py, app/services/notes.py, search.py,
dedup.py, emit.py — код не трогаем (докстринги сервисов при необходимости
поясняются одним абзацем: «MCP-слой срезает служебные поля — см. Фаза 9»).

## 1. Целевые контракты MCP (решения Олега, 2026-08-30)

Общее: `hint` — только при fail (§5.3); в успешных ответах его нет. Порядок
элементов меньше веса не меняет (id — связь цепочки search → get → update).

1. **memory_search** → результаты (где есть релевантность): `id, summary,
   created_at, updated_at`. Пусто (fail) → `results: []` + `hint`
   (тексты HINT_* сохраняются дословно). `warning` из ответа срезается
   (решение О.): логика деградации в сервисе остаётся, warning доступен
   в REST и логах, но MCP-выдачу не утяжеляет.
2. **memory_list** → `items[]`: `id, summary, created_at, updated_at`;
   наверху `total` (число, нужен для offset-пагинации). Fail (пусто /
   offset за пределом) → `items: [], total, hint`.
3. **memory_get** → по одной записи на запрошенный id:
   `id, text, created_at, updated_at`. `summary`, `summary_status`,
   `author` из ответа срезаются (summary — дубль начальных ~200 симв. text
   либо суммари по нему). Частичное исполнение batch — не fail: нашедшиеся
   отдаются, пропущенные id молча выпадают (как в FR-3). Fail = не найдено
   ничего → `notes: [], hint`.
4. **memory_save** → успех: `id, stored: true, summary_pending: true`
   (решение О.: флаг остаётся — модель сразу после save не удивляется
   fallback-содержанию в list/search). Дубль (fail): `id, stored: false, hint`
   (DEDUP_HINT сохраняется; id — id СУЩЕСТВУЮЩЕЙ заметки, полный text
   и флаг duplicated срезаются).
5. **memory_update** → `id, updated: true` | fail: `id, updated: false, hint`.
6. **memory_delete** → `id, deleted: true` | fail: `id, deleted: false, hint`.

Срезаются окончательно (из MCP-выдач): snippet, rrf_score, cosine,
summary_status, author, summary (в get), summary_pending (в update),
text дубля (в save), warning (в search), флаг duplicated как отдельное поле.

## 2. Что архитектору проанализировать (до постановки задач)

1. Точки маппинга в mcp.py: шесть обёрток вызывают сервисы и возвращают их
   dict напрямую. Определить одну установку: локальные срезатели/белые списки
   полей напротив каждого метода (запрещённые поля не только не добавлять,
   но и не «просачивать» при росте сервисных ответов).
2. Матрица тестов: какие тесты MCP-поверхности читают срезаемые поля
   (snippets, cosine, rrf_score, summary в get, DEDUP_HINT/текст дубля,
   warning) — составить список переписанных перед правкой кода.
3. Косвенные зависимые: openapi/схемы MCP-инструментов (аннотации), инстру
   описания TOOL_DESCRIPTIONS (упоминания snippet/summary в get требуют
   правки текста, обновление ~200–300 токенов инструкции), observability
   (log_tool_call: поля warning после среза — не потерять лог деградации:
   искать отдельный канал в логах, не в ответе).
4. REQUIREMENTS/ARCHITECTURE: разделы, где контракты выдачи описаны как
   единые для MCP+REST (§5.1, FR-1…FR-6, §5.3, §3.1) — при срезе на
   MCP-уровне их нужно переупаковать: «сервис возвращает полный контракт,
   MCP-слой отдаёт модели компактный §5.x (Фаза 9)». REST-контракты в
   доксах НЕ редактировать, добавить отдельный раздел.
5. E2E-чеклист по живому инстансу: /health, save (успех/дубль), search
   (результаты/пусто/короткий запрос), list (страница/за пределом),
   get (batch/пропуск/полный провал), update/delete (true/false),
   сравнение REST vs MCP на одном и том же id (нетленность REST).

## 4. Метрики успеха / критерии приёмки

- MCP-выдачи содержат только поля из §2 (проверяется тестами на белые списки).
- REST-контракты байт-в-байт прежние (существующие REST-тесты зелёные без правок).
- 473 passed → без роспуска, переписанные MCP-тесты включают фичи срезанных
  полей как «не присутствует в ответе».
- Замеры: memory_search top_k=5 ~2 КБ → ≤1.2 КБ; save-дубль ~2.2 КБ → ≤0.2 КБ;
  memory_get пары {id,text,...} — без summary/metadata-колонок.
- Найтикие edge-кейсы сохраняют поведение: hint-тексты дословно, порядок и
  пропуски в get, warning в REST жив.
